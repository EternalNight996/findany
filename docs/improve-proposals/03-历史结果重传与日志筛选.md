# 改善提案（三）：历史结果重传与日志筛选

| 项目 | 内容 |
| --- | --- |
| 提案名称 | 历史批次一键重传，替代手动批量同步服务器数据 |
| 改善类别 | 效率 + **安全（补齐漏传、避免人工二次外发）** |
| 提案人 | 【填写】 |
| 日期 | 【填写】 |

## 一、为什么提这个改善（现状与问题）

日常会遇到这几类情况：

1. **当时没传成功的**：网络不通、服务器波动、密钥过期，那几台的数据其实没上到服务器；
2. **服务器侧数据缺失**：事后查 HASH 查不到，才知道有几台漏了；
3. **要补历史批次**：客户或后工序要某一时段的记录。

**现在的做法**：人工找到当时的 `filter_result.xlsx`，把 Hash 一列复制出来，再手工逐个同步给服务器。

**问题（痛点）**：

| 痛点 | 说明 | 后果 |
| --- | --- | --- |
| 批量手工同步 | 几十上百台要一台台复制粘贴 | 慢、易错行 |
| **数据被人工复制、经手** | Hash / SN 被复制到剪贴板、表格、聊天工具 | **外发风险，可能变成客诉** |
| 判不清该不该重传 | 上次的"回传状态"列可能是旧的、不准 | 该传的没传、不该传的重复传 |
| 传了没凭据 | 手工同步没有回执 | 说不清 |
| 改坏原表 | 手工改回 Excel，没有备份 | 原始记录丢失 |

## 二、改善方案

**核心思路：直接拿当时的批次结果表（`filter_result.xlsx`）当输入，工具自动逐台重传并写回结果；人不需要复制任何一列数据。**

```
指定扫描目标（里面有历史 filter_result.xlsx）
      ↓
工具递归找出所有 filter_result.xlsx
      ↓
逐行判定：OA3 必需字段是否齐全（SN / ProductKeyID / HardwareHash / Baseboard）
      ↓
齐全 → 自动重传（含逐台实时计数）；不全 → 跳过
      ↓
回传过的行写回结果表（写回前自动备份）
```

**判定口径（关键，写清楚避免争议）**：

- 合格条件 = **四个 OA3 必需字段是否齐全**：SN（serial_number）/ ProductKeyID（product_key_id）/ HardwareHash（hardware_hash）/ Baseboard（baseboard_product）；
- 四个字段齐全 → **重新回传**（服务端对重复上报返回 `duplicate_accepted`，判为成功）；
- 缺任一字段 → **跳过**，不重传（这类台传也传不了），界面与日志里列出**缺哪些字段、共跳过几台**。

**能力对照**：

| 能力 | 说明 | 对痛点的作用 |
| --- | --- | --- |
| 批量自动重传 | 递归找出目录下所有 `filter_result.xlsx`，逐台重传 | 解决「慢、易错行」 |
| 字段齐全才传 | 缺任一必需字段直接跳过，不会传半条数据 | 解决「判不清」 |
| 跳过也说明原因 | 界面/日志给出「跳过 N 台（不满足 OA3 回传条件，未写回）」并列出缺哪些字段 | 补数据有方向 |
| 跳过的不写回 | 只有**真正回传过**的行才写回；整份都不满足条件时原文件一格不动 | 记录干净、原表不被污染 |
| 写回自动备份 | 写回前留 `.bak-时间戳` 备份 | 解决「改坏原表」 |
| 写回原子化 | 写临时文件 → 校验 → rename 替换；先探可写 | 不会写坏文件 |
| 逐台实时计数 | 「成功 / 冲突 / 失败」一台一变；文件级显示"完成（写回 N 格）""跳过 N 台" | 进度看得见 |
| 失败原因可见 | CLI 应答（`error_code` / `message`）写回「回传错误」列 | 一眼知道为什么失败 |
| 坏文件单独记录 | 读不动 / 写不动的文件记入 `_bad_files.txt`（状态 + 文件 + 原因） | 不会静默漏掉 |
| 结果可校验 | 末行输出 `R<...>R` 结论（`status` / `content`） | 平台可自动判 PASS / FAIL |

> 说明：工具界面上的提示文案还留着早期口径「只重传回传状态为空 / 失败 / dry-run 的行，成功与冲突（人工）跳过」，代码注释里也残留同样说法；**实际行为以上面的口径为准**——只要四个必需字段齐全，上次显示"成功"或"冲突(人工)"的台**同样会被重新回传**（重复上报由服务端返回 `duplicate_accepted`，判为成功）。建议同步修掉这处文案，避免操作人误解。

**安全性改善（本提案的价值）**：

- Hash / SN **不经过剪贴板、不经过聊天工具、不经过邮箱**，由工具直接从结果表读到、直接发给服务器；
- 审计落 `out/<时间>/upload-result.csv`，且**不含 Hash 与 SecretKey**；
- 全程按批次留档 + 备份，责任链清楚，减少「数据被客户拿到」的客诉。

## 三、实施步骤

1. 选一批已知漏传的历史数据（最好能对照服务器侧现状），先试跑。
2. 切「历史结果重传」模式，把「扫描目标」指向存放历史批次 `filter_result.xlsx` 的目录。
3. 先 `dry_run=true` 演练：核对「哪些会被传、哪些判定跳过」，确认字段口径无争议。
4. 正式重传：看逐台实时计数，结束后核对「成功 / 冲突 / 失败」。
5. 服务器侧抽查：挑 3~5 台查 HASH，确认能查到。
6. 处理异常：冲突（退出码 12）与失败清单按人工流程处理；`_bad_files.txt` 里的文件单独修。
7. 归档：把批次产物与 `.bak` 备份一起留档，写进作业指导书。

## 四、改善效果

| 指标 | 改善前 | 改善后 | 说明 |
| --- | --- | --- | --- |
| 重传 100 台耗时 | 【待实测】 | 【待实测】 | 自动逐台，无需人工复制 |
| 复制粘贴错行 | 会有 | 无（读表直传，不经过人） | 核心安全收益之一 |
| 数据是否经手 | 会（剪贴板 / 表格 / 聊天工具） | 不会 | 减少外发与客诉 |
| 该传 / 不该传 | 靠人判断 | 按字段齐全度统一判定 | 有唯一口径 |
| 原表安全 | 手改、无备份 | 自动 `.bak` + 原子写回 | 可回退 |
| 失败可见性 | 不知道 | 错误写回列 + `_bad_files.txt` | 可追责、可补 |

## 五、风险与应对

| 风险 | 应对 |
| --- | --- |
| 误判该传的行 | 口径只看四个必需字段，先 `dry_run` 演练核对清单 |
| 重复回传导致服务器重复数据 | 重复应答按约定口径处理（`duplicate_accepted`，需与服务器方确认是否算成功） |
| 写回改坏历史表 | 写回前 `.bak-时间戳` 备份 + 写临时文件校验后替换 |
| 历史表版本混乱 | 只递归标准文件名 `filter_result.xlsx`；批次目录按时间命名，天然有序 |
| 大批量重传压服务器 | 降低并发线程、加每批休眠，必要时分批跑 |

## 六、验收标准（做完怎么算成功）

- [ ] `dry_run` 演练清单与人工判断一致（抽 10 行核对）。
- [ ] 重传后服务器侧抽查 3~5 台，**能查到对应 HASH**。
- [ ] 缺字段的台被明确报为「跳过 N 台（不满足 OA3 回传条件，未写回）」并列出缺哪些字段。
- [ ] 结果表回写正确：只有真正回传的行被写回，且有对应 `.bak-时间戳` 备份。
- [ ] 批次产物齐全：`filter_result.xlsx` + `upload-result.csv`（不含 HardwareHash / ProductKey / SecretKey）+ `_bad_files.txt`（如有）。
- [ ] 末行 `R<...>R` 结论与实际一致（`status=true` 才代表通过）。
- [ ] 作业指导书明确：**禁止用复制粘贴 / 聊天工具 / 邮件传递 OA3 数据**。
