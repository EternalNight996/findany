# 改善提案（二）：日志筛选模式 —— OA3 日志自动上传

| 项目 | 内容 |
| --- | --- |
| 提案名称 | OA3 激活日志自动上传公司服务器，替代人工手工上传 |
| 改善类别 | **安全（数据外发管控）+ 效率** |
| 提案人 | 【填写】 |
| 日期 | 【填写】 |

## 一、为什么提这个改善（现状与问题）

**业务背景**：OA3.0 激活之后，需要把生成的对应日志文件上传到公司服务器上，这样才能查询到对应的 HASH 值。

**现在的做法**：人工把要上传的文件目录找出来，再手工上传（拷盘 / 聊天工具 / 邮件 / U 盘 / 远程等方式）。

**问题（痛点）**：

| 痛点 | 说明 | 后果 |
| --- | --- | --- |
| 数据经人手 | OA3 日志里有**完整 HardwareHash、ProductKeyID、SN、Baseboard** 等数据，人一旦经手就可能外发 | **客户共享 OA3 数据、后续客诉**（本次要改善的核心） |
| 渠道不可控 | 邮件、微信、U 盘、共享盘……哪条路传的说不清 | 无法追溯、无法审计 |
| 会漏传 / 传错 | 漏一个文件，服务器就查不到那台的 HASH | 客诉、返工 |
| 不知道传没传成功 | 手工上传没有回执，只能靠"我记得传了" | 责任说不清 |
| 重复劳动 | 每批都要人工挑文件、人工上传 | 慢、占人 |

## 二、改善方案

**核心思路：人只负责「把要传的文件目录放上去」，软件自动完成上传并返回结果。数据不再经过人手转发。**

```
放目录（要上传的文件所在目录）
      ↓
工具自动筛选出应上传的日志（本工具=日志筛选模式）
      ↓
自动调上传 CLI 逐台回传公司服务器
      ↓
返回上传结果（成功 / 冲突 / 失败）+ 审计留档
```

**能力对照**：

| 能力 | 说明 | 对痛点的作用 |
| --- | --- | --- |
| 判型自动识别 | 自动识别 `etest(OA3)` / `etest` / `e-autotest` / 海格旧测试 2、3 | 不用人工挑文件 |
| 字段提取 | 自动提取 SN / ProductKeyID / HardwareHash / Baseboard（HardwareHash 4000 字符全值） | 不漏台 |
| 自动回传 | 提取成功后逐台调上传 CLI；超时 60s、退避重试 3 次 | 解决「漏传、重复劳动」 |
| 回传判定 | 退出码 0 且应答 `status∈{accepted, duplicate_accepted}` 双确认=成功；`12`=冲突转人工；其余=失败 | 解决「不知道传没传成功」 |
| 结果留档 | `out/<时间>/filter_result.xlsx` + `upload-result.csv`（审计 CSV 固定 10 列：时间 / SN / 日志文件 / 回传状态 / 退出码 / resp_status / request_id / 尝试次数 / 耗时s / 错误） | 可追溯、可审计 |
| 无人值守 | 配置 `auto_start=true`，启动即自动「检测→回传→完成处理」 | 产线不用人盯 |
| 不误判 PASS | 数据为空、或开了回传却没真回传（一台没匹配 / 一台没回传 / 有冲突）→ **不判 PASS** | 不会"看着完成了其实漏了" |
| 演练模式 | `dry_run=true` 只组包校验、不打网 | 上线前先验证 |

**安全性改善（本提案的核心价值）**：

1. **数据闭环**：日志从本机目录 → 上传 CLI → 公司服务器，**唯一出口是公司服务器**，不经邮件 / 聊天工具 / U 盘，**不再与客户共享 OA3 数据**。
2. **人看不到、也不用碰**：操作人只操作目录和看点结果，不需要打开日志内容、不需要复制 Hash。
3. **审计齐全但不泄密**：每批都有批次目录 + Excel 明细 + `upload-result.csv`；审计 CSV 只记 SN、日志文件名、回传状态/退出码/request_id、尝试次数、耗时、错误，**不含 HardwareHash / ProductKey / Baseboard / SecretKey**。
4. **密钥不入库**：SecretKey 只存在本机配置（已 gitignore，不进源码 / 日志）。
5. **失败拦住**：回传不成功就不判 PASS，界面与 `R<...>R` 结论共用同一套判定，杜绝"假完成"。

## 三、前提条件与需沟通事项（必须先落实）

> 这一节是本提案能否落地的前提，需要与公司（服务器 / 开发方）逐条确认。

### 3.1 前提条件

| # | 前提条件 | 责任方 | 状态 |
| --- | --- | --- | --- |
| 1 | 我们工厂的**内部服务器要能临时访问到外网**（否则传不出去） | 工厂 IT / 网络 | 【待确认】 |
| 2 | 明确放行方式（域名 / IP / 端口白名单，还是临时开通） | 工厂 IT + 公司服务器方 | 【待确认】 |
| 3 | 上传所用的公网服务器地址可用、可连通 | 公司服务器方 | 【待确认】 |

### 3.2 需要对方（公司 / 开发方）提供的东西

| # | 需要提供 | 用途 | 状态 |
| --- | --- | --- | --- |
| 1 | **一个 CLI 的 Demo 可执行程序**：能指定路径文件上传，并返回上传结果 | 我们先用它验证「能不能传、结果怎么读」 | 【待提供】 |
| 2 | **上传用的公网服务器域名或 IP** | 配置上传目标 | 【待提供】 |
| 3 | **需要的子测试功能数据**，例如 OA3 Key 的完整数据、产品 SN 等 | 做联调测试数据 | 【待提供】 |

### 3.3 建议一并确认的口径

- 上传成功的判定标准（是否就是 `status=accepted / duplicate_accepted`）；
- 重复上传（`duplicate_accepted`）算成功还是要转人工；
- 冲突（退出码 `12`）由谁处理、多久内处理；
- 上传失败的可重试次数与时间窗；
- 服务器侧是否需要固定出口 IP（若需要，提前报给网络）。

## 四、实施步骤

1. **准备期**：落实 3.1 网络前提 → 拿到 3.2 的 CLI Demo / 服务器地址 / 测试数据。
2. **验证期（不影响生产）**：用 CLI Demo 在本机小批量试传，确认「能连通、能上传、能读到结果」。
3. **工具配置**：本工具切「日志筛选」模式，填上传 CLI 路径、参数模板、SecretKey（本机配置）、超时与重试。
4. **演练**：`dry_run=true` 空跑一轮，核对提取字段是否齐全、组包是否正确。
5. **试运行**：正式回传，先跑 1 批真实日志，逐台核对上传结果与服务器记录是否一致。
6. **上线固化**：写作业指导书（放哪个目录、点哪个按钮、怎么看结果、失败找谁）+ 培训 1 次。
7. **持续**：批次产物按月归档；每周看一次失败 / 冲突清单。

## 五、改善效果

| 指标 | 改善前 | 改善后 | 说明 |
| --- | --- | --- | --- |
| 数据外发渠道 | 邮件 / 微信 / U 盘 / 共享盘，不可控 | 只有公司服务器一条路 | **核心安全收益** |
| OA3 数据是否经人手 / 与客户共享 | 会 | 不会 | 直接减少后续客诉 |
| 单批上传耗时 | 【待实测】 | 【待实测】 | 自动逐台，参考实测：6 台份日志提取+回传 1.23s |
| 漏传 | 会发生 | 不判 PASS、必须处理 | 判定与结论同一套 |
| 上传成功与否 | 靠记忆 | 有回执 + 审计 CSV | 可追溯 |
| 人工 | 挑文件 + 手工传 | 放目录 + 看点结果 | 人工减少 |

## 六、风险与应对

| 风险 | 应对 |
| --- | --- |
| 外网访问开不了（前提条件不满足） | 提前用 3.1 清单找 IT 确认；先做内网 / 本机 Demo 验证，网络一开通即可上线 |
| 服务器地址或密钥变更 | SecretKey 与地址都在本机配置里，改一处即可，不用改程序 |
| 上传失败被当成完成 | 工具不判 PASS（`status=false`），必须处理后重跑 |
| 重复上传造成数据重复 | 重复应答 `duplicate_accepted` 按约定口径处理（建议算成功，需确认） |
| 误传不该传的文件 | 上传类型限定 `etest(OA3)`；扫描目录固定；正式回传前先 `dry_run` 演练 |
